# 可用性测试数据分析：从原始记录到可执行洞见

**适用单元**: W14 — 数据复盘与作品库凝练  
**来源**: Interaction Design (Rogers, 2023) Ch14-15 + Lean UX (Gothelf, 2022) Ch15

---

## 一、原始数据处理：质性编码框架

出声思考测试结束后，你手里有：
- 录屏视频 + 时间戳笔记
- 观察员的手写记录
- 严重度量表评级

### 第一步：数据整合（Affinity Diagramming 亲和图法）

将所有**观察到的问题瞬间**写在便利贴上，一张便利贴只写一个问题。  
将便利贴分组聚类，让主题自然浮现：
- **一级分组**：流程断裂 / 认知摩擦 / 视觉混乱 / 语言歧义
- **二级聚类**：在同类问题中寻找最小公约的根因

> 💡 数字工具替代方案：FigJam、Miro 的便利贴模式完全胜任。

## 二、严重度排序（Severity Rating Matrix）

Nielsen 的严重度评级使用 0–4 量表：

| 评级 | 描述 | 典型表现 | 建议行动 |
|:---|:---|:---|:---|
| 0 | 不是问题 | 用户成功完成，无卡顿 | 记录即可 |
| 1 | 轻微瑕疵 | 用户发现了但快速自我修正 | 下一版迭代修复 |
| 2 | 中等障碍 | 用户需要思考并绕行才能完成 | 优先修复 |
| 3 | 重大问题 | 用户任务失败，但在提示后可继续 | 立即修复 |
| 4 | 灾难性崩溃 | 用户完全无法完成，且意志崩溃 | 发布前必须解决 |

> **严重度 = f(发生频率, 影响深度, 时间损耗)**  
> 一个 4 级问题优先于十个 1 级问题。

## 三、量化补充：任务成功率与时间指标

即使是"游击测试"，也应至少收集：

- **任务完成率 (Task Completion Rate)**：成功完成该任务的参与者 / 总参与者
- **错误次数** / **救援请求次数**（用户说"我放弃了"或问"怎么操作"的次数）
- **操作时间 (Time-on-Task)**：记录用户开始操作到完成/放弃的时长

### SUS（系统可用性量表）的快速复盘用法

SUS 是一个 10 道题、5 档评分的标准化问卷，可在测试后 2 分钟内完成。  
**评分公式**：奇数题（正面）减 1，偶数题（负面）用 5 减；总和乘以 2.5 = 最终分数（0-100）。

| SUS 分段 | 评价 |
|:---|:---|
| > 85 | 优秀（Excellent） |
| 71-85 | 良好（Good） |
| 52-70 | 一般（OK） |
| < 52 | 需要改进（Poor） |

## 四、从数据到行动：修复优先级决策

整合严重度矩阵与频率数据后，绘制**修复影响矩阵**：

```
           高影响
            |
   四象限   |  [立即修复] ← 高严重度+高频
            |
低频 -------+------- 高频
            |
   [积压    |  [快速修复] 
    观察]   |
            |
           低影响
```

**核心原则：以故事驱动选择，而非以工作量驱动。**  
选择修复那些"能改变用户整体旅程故事"的问题，而不仅仅是"好修的"问题。
