# Workflow: 从零开始构建设计 (Starting from Scratch)

## Prerequisites & Context (前提条件与上下文)

**适用场景 (WHEN):**
在启动全新应用的 UI 设计、规划新功能模块，或面临设计初期因细节过多而导致进度停滞时使用此工作流。

**核心目的 (WHY):**
避免在设计初期陷入对“外壳”(Shell) 和低级细节（如阴影、精确颜色）的过度纠结，防止因“过度设计”或未考虑实现难度的理想化设计而阻碍产品的实际交付。本工作流旨在通过约束设计过程，引导 Agent 或设计师聚焦于核心功能和一致的视觉个性。

> **深度理论获取 (Progressive Disclosure):**
> 如果在执行过程中需要理解本工作流背后的深层产品设计哲学，请通过 Runtime Agent 运行以下命令获取深度理论支持：
> ```bash
> bash scripts/query_theory.sh "Why is it important to start with a feature instead of a layout when designing an app?"
> bash scripts/query_theory.sh "What is the psychological impact of designing in grayscale first?"
> ```

## Comprehensive Guide & Best Practices (综合指南与最佳实践)

### 1. 从核心功能开始，而非全局布局 (Start with a Feature, Not a Layout)
不要一开始就尝试“设计整个应用”的框架（例如顶部导航栏、侧边栏、Logo 位置等）。应用本质上是功能的集合，在没有功能细节支撑的情况下决定导航逻辑是毫无意义且令人沮丧的。

* **行动指南:**
  * 直接选取应用中最核心的一项功能开始设计（例如：机票预订系统的“搜索航班”功能）。
  * 罗列该功能必需的界面元素（输入框、按钮等），并优先完成这一特定区域的设计。
  * **禁止操作:** 在完成几个核心功能设计之前，禁止进行全局 Shell（导航/容器约束）的设计。

### 2. 细节后置与低保真设计 (Detail Comes Later)
在构思阶段，过早引入高保真细节（字体、阴影、图标）会分散对功能逻辑和视觉层级的注意力。

* **行动指南 (Hold the Color):**
  * 初始设计必须在**灰度 (Grayscale)** 下进行。强制自己仅通过间距 (Spacing)、对比度 (Contrast) 和尺寸 (Size) 来建立清晰的视觉层级。
  * 将草图视为“一次性消耗品”，快速探索布局方案，一旦决定就丢弃它们，不要在静态图上过度投入。
  * *(启发式技巧)* 想象使用粗体马克笔 (Thick Sharpie) 在纸上画图，这种限制会阻止你关注微小的像素级细节。

### 3. 避免过度设计与边缘用例焦虑 (Don't Design Too Much)
尝试在抽象的设计工具中解决所有交互细节和边缘用例（例如：用户有2000个联系人时界面如何展示）是低效的。

* **行动指南 (Work in Cycles):**
  * **短周期迭代:** 设计下一个功能的“最小可用版本” -> 立即将其转换为真实代码/原型 -> 在真实环境中发现问题并迭代 -> 再回到设计模式进行下一个功能。
  * **悲观主义原则 (Be a Pessimist):** 预期功能在开发时会非常困难。不要在设计中包含尚未准备好开发的功能（例如：评论系统中的“文件附件”）。
  * **推迟“非必需品”:** 优先设计和发布最小可用版本。如果某个特性只是“锦上添花”(nice-to-have)，请推迟它的设计，确保团队永远有可以立即交付的成果。

### 4. 赋予设计特定的“性格” (Choose a Personality)
设计表面上的“调性”是由几个具体的、可度量的因素决定的。

* **字体选择 (Font Choice):**
  * 优雅/经典 -> 衬线字体 (Serif)
  * 趣味/活泼 -> 圆体无衬线字体 (Rounded Sans Serif)
  * 中性/简洁 -> 常规无衬线字体 (Neutral Sans Serif)
* **颜色心理学 (Color):**
  * 蓝色 (Blue) = 安全、熟悉
  * 金色 (Gold) = 昂贵、精致
  * 粉色 (Pink) = 有趣、不严肃
* **圆角半径 (Border Radius):**
  * 小圆角 = 中性
  * 大圆角 = 活泼/趣味
  * 直角 (无圆角) = 严肃/正式
  * **铁律:** 必须保持绝对的一致性，严禁在同一界面混用直角和圆角。
* **文案基调 (Language):**
  * 使用的词汇与视觉元素同样重要。少带个人感情色彩的词汇显得专业/官方，而轻松的语言则显得友好。

## If/Then Troubleshooting Logic (故障排除逻辑)

* **IF** 你发现自己被卡住，不知道导航栏应该放在左边还是上边时：
  * **THEN** 立即停止全局外壳 (Shell) 设计，挑出应用最核心的一个功能模块，只专注于设计这个功能的输入和输出元素。
* **IF** 设计看起来缺乏重点，所有元素都在争夺用户的注意力：
  * **THEN** 去除所有颜色（转换为灰度），重新依靠留白、字体粗细和尺寸大小来建立清晰的层级结构。
* **IF** 某个边缘用例（例如日历中同时发生两个事件）在设计工具中极难排版：
  * **THEN** 停止在抽象层面的无休止推演。实现基础版本的代码，在真实运行的浏览器/环境中测试并修复该问题。
* **IF** 某个正在设计的功能（如评论附带上传多文件）被评估为需要大量后端支持才能实现：
  * **THEN** 砍掉该功能的复杂部分。回退并发布一个仅支持纯文本评论的版本，保证有可交付的产品。
* **IF** 界面的视觉感受显得不专业或拼接感强：
  * **THEN** 检查圆角和排版体系。是否存在既有直角按钮又有大圆角卡片的混用情况？统一它们以修复个性撕裂。

## Verification Checklists (验证清单)

- [ ] 是否直接从具体的核心“功能 (Feature)”着手设计，而不是从顶部导航或侧边栏开始？
- [ ] 初始的布局和层级探索是否在**灰度 (Grayscale)** 下完成，证明其结构在无色彩依赖下依然清晰？
- [ ] 是否应用了“悲观主义”策略，排除了暂时无法实现的复杂功能（如附件上传），仅设计了最小可用版本？
- [ ] 是否在设计陷入无休止的抽象边缘用例前，将阶段性成果转换为真实的可交互环境（代码/原型）？
- [ ] 是否明确定义了设计的“性格”（专业、趣味、经典等），并通过一致的字体、颜色、圆角和文案来体现？
- [ ] **视觉一致性校验:** 检查所有容器和组件的 `border-radius`，确保界面中没有直角和圆角的混乱混搭。
