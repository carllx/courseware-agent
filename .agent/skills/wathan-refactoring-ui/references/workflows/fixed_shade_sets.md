# 固定色阶集合工作流 (Fixed Shade Sets)

## Prerequisites & Context (前提与背景)
- **WHY (为什么要使用固定色阶)**: 动态计算颜色（例如使用 Sass/Less 的 `lighten()` 或 `darken()` 函数，或者用透明度蒙版）在短时间内看似方便，但最终会导致不可预测的色彩、脏污的色调和维护的噩梦。预定义的固定色阶系统确保了调色板的一致性、可维护性和纯净度。
- **WHEN (什么时候使用)**: 在设计系统的基础阶段构建调色板时，或者在重构充满随意色值的陈旧 CSS 代码时。

## Comprehensive Guide & Best Practices (综合指南与最佳实践)
1. **摒弃自动加深/变浅函数 (Avoid Lighten/Darken Functions)**:
   - 计算出来的颜色通常缺乏生机。因为简单的亮度调整忽略了“感知亮度”和色相偏移的自然规律。
   - 人为地挑选并固定一组颜色（例如 9 个级别），可以确保每一个阴影在视觉上都是经过优化的。
2. **选择基准色 (Base Color)**:
   - 先不要考虑整个色阶，**先挑选出该颜色的基准色（Base Color，通常定义为 500 级）**。
   - 这是一个该颜色在不考虑任何其他状态下的“完美形态”——它足够鲜艳，可以作为图标或色块，如果它被用作按钮的背景，它应该提供足够的对比度。
3. **构建预定义的调色板**:
   - 围绕这一个基准色（500），向上向下人工构建预定义的色板，如 100（极浅的背景色）到 900（极深的文字色）。这套系统在 TailwindCSS 中被广泛应用。

## If/Then Troubleshooting Logic (故障排除逻辑)
- **IF** 你在 CSS 中看到大量的 `lighten(primary, 20%)` 或 `rgba(black, 0.5)`：
  - **THEN** 它们会导致界面上存在数十个不可控的微小差异。替换为系统预定义的色阶（如 `primary-200` 或 `gray-500`）。
- **IF** 选定了一个绝美的基准色，但发现它作为按钮背景时无法看清白色文字：
  - **THEN** 该基准色的亮度太高，无法通过无障碍对比度测试。你必须将 600 或 700 级别的颜色重新指定为“主操作基准色”，或者将按钮的文本改为深色。
- **IF** 在不同组件复用颜色时发现亮度不匹配：
  - **THEN** 因为没有遵循固定色阶的编号约定。如果系统规定所有边框使用 200 级别，所有次要文本使用 500 级别，那就必须严格遵守，而不是为每个组件单独挑选颜色。

## Verification Checklists (验证清单)
- [ ] 系统中所有的颜色变化是否都来自预定义的固定集合（如 `blue-500`, `blue-600`）？
- [ ] 是否彻底消除了样式表中对透明度遮罩和 `lighten/darken` 函数的滥用？
- [ ] 每种颜色的基准色（Base Color）是否都是该色系中最具代表性且平衡的状态？
- [ ] 代码库是否能仅凭颜色变量的名称（例如 900）就预测出该颜色的用途（如用于文本）？
