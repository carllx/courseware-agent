# 工作流：网格被高估了 (Grids are Overrated)

## Prerequisites & Context (前提与背景)
- **WHY (为什么需要此工作流)**：传统的 12 列网格系统在很多情况下会限制设计师的灵活性。过分拘泥于“必须将元素对齐到网格列”会导致元素内部比例失调或被迫拉伸。
- **WHEN (何时使用)**：在设计组件内部布局、复杂的表单、数据密集型界面时，决定元素的具体宽度。

## Comprehensive Guide & Best Practices (全面指南与最佳实践)
1. **不要让网格决定内容宽度 (Don't let the grid dictate content width)**
   - 网格系统适合大尺度、整页级别的宏观布局（如划分侧边栏和主内容区）。
   - 对于组件级别，元素的宽度应当由其**内容本身**决定，而不是它占据了多少个“列”。
2. **给元素其所需的空间**
   - 如果一个表单输入框只需要填写邮政编码，让它保持较短的固定宽度，而不是为了填满半个容器而拉伸它。
   - 强行对齐到网格会让较短的内容产生尴尬的留白，降低可读性和界面的精致感。
3. **基于内容的独立布局 (Content-Driven Layout)**
   - 使用 Flexbox 或 CSS Grid 中的自适应/固有尺寸特性（如 `max-content`, `fit-content`）来处理组件内部的排版，而不是传统的比例网格。

## If/Then Troubleshooting Logic (故障排除逻辑)
- **IF** 表单元素看起来被过度拉伸，导致用户的视线需要在标签和输入区域之间移动过长距离：
  - **THEN** 打破网格约束，将输入框的宽度设定为与其预期输入内容长度相匹配的固定或最大宽度。
- **IF** 设计师在为了对齐 12 列网格而在组件内部增加不自然的间距：
  - **THEN** 放弃组件内部的传统列网格，转而采用前面定义的“间距与尺寸系统 (Spacing and sizing system)”来进行绝对间距控制。

## Verification Checklists (验证清单)
- [ ] 宏观页面布局和微观组件布局是否被区分对待？
- [ ] 文本输入框等控件的宽度是否合理反映了它们预期内容的长度？
- [ ] 是否避免了为追求形式上的网格对齐而强行拉伸组件内部元素的做法？
