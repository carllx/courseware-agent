# 目标导向设计：非用户目标工作流 (Nonuser Goals)

## Prerequisites & Context (前提条件与上下文)
**WHY（为什么使用）**：
虽然目标导向设计的核心是“最终用户（End User）”，但产品开发永远不是在真空中进行的。为了确保产品的商业可行性（Viability）和技术可行性（Feasibility），设计师必须识别并满足非用户目标（Nonuser Goals）。如果一个产品满足了用户但惹恼了购买者（如企业 IT 采购部门）或导致公司破产，那么它也是失败的。
**WHEN（何时使用）**：
- 在产品战略规划和利益相关者访谈（Stakeholder Interviews）阶段。
- 在对功能进行优先级排序时（权衡用户体验与商业变现时）。
- 当向高层管理团队或客户汇报设计方案时，需要证明设计如何支撑业务。

## Comprehensive Guide & Best Practices (综合指南与最佳实践)
《About Face》将非用户目标分为三大类。设计团队需要对其进行显性化，并将其与用户目标整合。

### 1. 客户/购买者目标 (Customer/Purchaser Goals)
- **定义**：客户是掏钱购买产品的人，但不一定是使用产品的人（在企业级 B2B 软件、儿童教育软件中尤其明显）。
- **常见目标**：易于部署维护、降低培训成本、数据安全与合规、控制预算、管理人员监控员工效率。
- **最佳实践**：在设计 B2B 系统时，必须为购买者（如 IT 管理员或部门经理）设计专属的“次要角色（Secondary Persona）”，提供管理仪表盘或权限配置系统，让他们看到产品的“管理价值”。

### 2. 商业/企业目标 (Business/Corporate Goals)
- **定义**：开发和发布该产品的公司试图达成的目标。
- **常见目标**：增加收入/利润、扩大市场份额、击败竞争对手、提升品牌知名度、留住现有用户。
- **最佳实践**：设计师必须理解产品的商业模式。如果商业目标是“增加广告点击”，直接增加弹窗会破坏用户目标。优秀的设计应找到结合点，例如在用户自然完成任务的节点（如游戏通关后）展示高度相关的赞助内容。

### 3. 技术目标 (Technical Goals)
- **定义**：开发团队或系统架构试图保持的技术标准。
- **常见目标**：节省内存、重用现有代码库、保证跨平台一致性、维护数据库完整性、在截止日期前发布。
- **最佳实践**：技术目标通常是内部的，**绝不能以牺牲用户目标为代价直接暴露给用户**（例如因为数据库限制而要求用户输入奇怪的格式）。设计师需要与工程师协作，在保持技术可行性的同时，用优雅的交互掩盖底层复杂性。

## If/Then Troubleshooting Logic (If/Then 故障排除逻辑)
- **IF** 商业目标（如强制收集用户隐私数据）与主要人物角色的目标（如安全感和效率）发生直接冲突，**THEN** 设计师必须成为用户的代言人。提出折中方案：通过提供明确的价值交换（“授权位置以获得精准天气”）来吸引用户，而不是采用阻断式强制收集。
- **IF** 技术团队以“现有框架不支持”为由拒绝一个关键的交互设计，**THEN** 追问该技术限制的边界。探讨是否可以通过修改框架、使用第三方库或者采用“视觉上相似但技术实现更简单”的替代方案来达成同样的用户目标。
- **IF** 购买者（客户）要求添加大量用户根本不需要的“打卡”或“监控”功能，**THEN** 尝试通过数据可视化或后端汇总的方式满足购买者的管控需求，而尽量减少前端操作对最终用户日常工作的干扰（如采用自动化日志记录代替手动填表）。

## Verification Checklists (验证清单)
- [ ] 是否在项目初期列出了明确的商业目标清单（如预期提升的具体指标）？
- [ ] （针对 B2B 或特殊产品）是否明确区分了“购买者”与“使用者”，并分别了解了他们的目标？
- [ ] 界面设计是否优雅地隐藏了技术限制，而不是将技术难题推给用户去解决？
- [ ] 当非用户目标与最终用户目标发生冲突时，是否找到了能够兼顾双方诉求的“双赢”设计模式？
- [ ] 设计方案在进行汇报时，是否能够清晰阐述它如何帮助企业实现特定的商业/战略目标？
