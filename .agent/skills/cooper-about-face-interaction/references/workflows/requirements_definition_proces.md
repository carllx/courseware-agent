# 交互设计工作流：需求定义过程 (Requirements Definition Process)

## 1. Prerequisites & Context (前提与背景：WHY & WHEN)
> [!NOTE]
> **WHY (为什么需要需求定义)**
> 在目标导向设计中，需求定义是连接定性用户研究（如人物角色 Personas）与交互框架（Framework）的桥梁。传统开发往往将“需求”等同于“功能清单”，而真正的交互需求必须是基于用户情境的、解答“用户必须能够做什么”的陈述，而非具体的技术实现。
> 
> **WHEN (何时应用此工作流)**
> 在完成用户调研并成功建立人物角色 (Personas) 之后，进入具体界面设计之前。此时需要提炼出具有指导意义的设计蓝图。

## 2. Comprehensive Guide & Best Practices (综合指南与最佳实践)

### 2.1 第一步：明确问题与愿景
- **问题陈述 (Problem Statement)**: 一句话总结当前产品缺乏什么、给业务和用户带来了什么阻碍。（如：由于缺乏统一的报表系统，用户必须手动导出数据，导致效率低下且容易出错）。
- **愿景陈述 (Vision Statement)**: 高层次的宏伟蓝图，描述产品成功后的状态，不仅要满足用户体验目标，也要对齐商业目标。

### 2.2 第二步：头脑风暴 (Brainstorming)
- **消除技术约束**: 暂时抛开技术限制，自由设想可能的交互模式。
- **避免过早定局**: 这个阶段不是为了选定最终方案，而是为了清空团队关于“它应该是什么样”的固有偏见。

### 2.3 第三步：识别人物角色的期望
- 每个主要人物角色 (Primary Persona) 对产品的心理模型是什么？
- 他们认为数据应该如何组织？他们期望怎样的系统响应节奏？

### 2.4 第四步：构建情境场景剧本 (Context Scenarios)
- **定义**: 基于主要人物角色的一天，以故事形式描述他们如何使用即将设计的系统来实现终极目标。
- **原则**: 必须是**非界面层面的 (Interface-free)**。不要写“点击右侧按钮”，而是写“系统主动呈现了关键指标”。
- **目标**: 关注流程、信息流向、物理环境和交互频次。

### 2.5 第五步：提取并梳理设计需求
基于场景剧本，提取三大类需求：
1. **数据需求 (Data Requirements)**: 系统需要展示或接收什么实体数据？（如：客户联系方式、历史订单）。
2. **功能需求 (Functional Requirements)**: 用户或系统需要执行什么动作？（如：对数据进行排序、一键发送邮件）。
3. **环境需求 (Contextual/Environmental Requirements)**: 物理或技术环境的限制？（如：强光下的可视度、单手操作、低带宽）。

## 3. If/Then Troubleshooting Logic (故障排除与逻辑分支)

- **IF** 提取出的功能需求发生了相互冲突（比如：需要极其详尽的数据展示 vs. 需要一目了然的简单视图）：
  - **THEN** 回归人物角色体系。永远以**主要人物角色 (Primary Persona)** 的终极目标为最高优先级，次要人物角色的需求必须妥协或通过高级折叠面板解决。
- **IF** 业务干系人试图强塞与情境场景无关的功能：
  - **THEN** 要求干系人说明该功能属于哪个具体的人物的哪一个场景。如果无法映射到现有情境，则坚决拒绝或将其列入低优先级待办。

## 4. Verification Checklists (验证清单)

- [ ] 是否已确立主要、次要等人物角色层级？
- [ ] 情境场景剧本是否完全剥离了特定的界面按钮或布局描述？
- [ ] 所有列出的数据需求和功能需求是否都能直接追溯到情境场景中的某一步？
- [ ] 是否充分考虑了用户所在的物理环境、硬件设备和网络状况（环境需求）？
