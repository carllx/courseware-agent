# 交互设计工作流：服务设计框架 (Service Design Framework)

## 1. Prerequisites & Context (前提与背景：WHY & WHEN)
> [!TIP]
> **WHY (为什么需要服务设计)**
> 现代产品的体验很少局限于单一的屏幕。用户体验是由跨越物理、数字、人工渠道的多个**接触点 (Touchpoints)** 共同构建的。服务设计框架确保数字界面（如 App）能够与后台流程、运营人员和物理环境无缝衔接。
> 
> **WHEN (何时应用此工作流)**
> 当产品涉及线上线下融合 (O2O)、跨端协作（如移动端+桌面端+客服支持）或多角色参与的复杂生态时，必须在具体的数字交互设计之前建立服务设计蓝图。

## 2. Comprehensive Guide & Best Practices (综合指南与最佳实践)

### 2.1 构建体验地图与服务蓝图
服务设计蓝图 (Service Blueprint) 包含以下几个核心层级（从前到后）：
1. **客户旅程 (Customer Journey)**: 用户随时间推进的动作、心理状态、情绪曲线。
2. **前台接触点 (Front-stage Touchpoints)**: 用户直接可见的实体环境、数字界面、员工沟通。
3. **可见度线 (Line of Visibility)**: 区分用户看得到和看不到的操作。
4. **后台互动 (Back-stage Interactions)**: 支持前台活动的内部员工流程或自动化系统行为。
5. **内部交互线 (Line of Internal Interaction)**: 区分直接支持人员与底层设施。
6. **支撑系统 (Support Processes)**: 数据库、第三方 API、核心业务规则。

### 2.2 识别并优化触点
- **触点一致性**: 确保用户在所有渠道感受到相同的品牌声音、逻辑模型和交互模式。
- **信息无缝流转**: 当用户从数字端切换到人工客服时，客服必须能即时获取用户的数字端行为上下文。

### 2.3 异常拦截与服务恢复
- 服务不仅关于“正确运作时的情况”，更是关于在发生问题时如何优雅地“恢复”。设计必须包含针对延误、故障、人为错误的预案。

## 3. If/Then Troubleshooting Logic (故障排除与逻辑分支)

- **IF** 用户在移动端的请求响应过慢或频繁报错：
  - **THEN** 审查蓝图中的“后台互动”或“支撑系统”，这往往是由于底层 API 无法支持前台设计的即时交互导致的。需要设计优雅的加载或异步处理界面。
- **IF** 用户在跨渠道转移时流失率极高：
  - **THEN** 检查不同触点间的摩擦。是否要求用户重新验证身份？是否丢失了上下文？必须实现跨端状态的强一致性共享。
- **IF** 现场人员 (如外卖员、售后) 与软件系统脱节：
  - **THEN** 需要专门为这些后台服务提供者建立特定的人物角色并设计他们的支撑工具，提升他们的效率等同于提升最终用户的体验。

## 4. Verification Checklists (验证清单)

- [ ] 是否绘制了完整的服务蓝图，涵盖用户目标达成的前置、进行中和后续所有阶段？
- [ ] 蓝图中是否明确划分了“可见度线”，并阐明了前后台的数据交互边界？
- [ ] 所有的实体触点和数字触点在视觉语言与品牌基调上是否高度统一？
- [ ] 服务蓝图是否涵盖了极端情况（如高峰期拥堵、系统宕机）下的服务降级和恢复策略？
