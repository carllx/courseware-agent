# 工作流：目标导向设计 (Goal-Directed Design)

## 1. 前置条件与上下文 (Prerequisites & Context)
**为何需要 (WHY)**: 
这是 Alan Cooper 提出的核心方法论。传统软件开发往往是“技术导向”或“功能导向”的，导致界面是底层代码逻辑的映射，用户被迫像机器一样思考。目标导向设计（GDD）主张以**理解和满足最终用户的根本目标（Goals）**为核心驱动力，超越单纯的任务（Tasks）堆砌。
**何时使用 (WHEN)**:
作为贯穿整个产品生命周期的元框架。从项目初期的研究、概念生成，到详细界面设计和评估。

## 2. 综合指南与最佳实践 (Comprehensive Guide & Best Practices)
GDD 由六个连贯的阶段构成：
1. **研究 (Research)**：
   - 抛弃问卷，走向实地。采用人种学访谈（Ethnographic Interviews）和上下文探究，观察用户实际的行为模式、工作流和痛点。
2. **建模 (Modeling)**：
   - 综合研究数据，创建**角色 (Personas)**。Persona 不是市场划分（如“25岁女性”），而是基于行为模式和目标建立的原型（如“追求无缝同步的效率至上者”）。
3. **需求定义 (Requirements Definition)**：
   - 利用 Persona 演练场景（Scenario）。基于场景提取在数据、功能和情境上的具体需求。
   - 重点关注体验目标（怎么感觉）、最终目标（要做成什么）和人生目标。
4. **框架定义 (Framework Definition)**：
   - 设计产品的骨架。建立信息架构、主要视图结构（UI 模式）和核心导航机制。
   - 决定功能模块如何在屏幕上组织，以最小化摩擦（Excise）。
5. **详细设计 (Refinement)**：
   - 细化交互和视觉。设计具体的控件状态、微交互、视觉隐喻和布局细节。遵循“设计三个层次”和“消除摩擦”的原则。
6. **支持开发 (Support)**：
   - 设计师与开发人员紧密合作，解决实施过程中出现的技术限制和边界情况，确保设计意图不走样。

## 3. If/Then 故障排除逻辑 (If/Then Troubleshooting Logic)
- **If** 团队在功能优先级上争论不休，每个人都说“用户可能需要这个”，**Then** 必须立刻回到 Persona 身上。提问：“我们的主要角色 (Primary Persona) 为了实现他的核心目标，是否必须依赖这个功能？”如果不是，将其降级或砍掉。
- **If** 用户在测试中能够完成任务（Task），但过程很痛苦且抱怨连连，**Then** 说明设计只满足了任务，没有满足“目标”（尤其是体验目标）。需要审查流程，寻找并消除摩擦（如减少点击、加入智能默认值）。
- **If** 开发团队认为框架定义阶段的设计无法在现有架构下实现，**Then** 不应直接放弃设计。设计师应与工程师一起探究限制的本质，寻找能达到相同体验目标的替代交互模式，而不是盲目退回到最容易写代码的糟糕界面。

## 4. 验证检查表 (Verification Checklists)
- [ ] 所有的设计决策是否都能直接追溯到一个具体的 Persona 的目标？
- [ ] 是否明确区分了“任务”（用户为了达到目标被迫做的事）和“目标”（用户真正想要的最终结果）？
- [ ] 框架设计是否优先照顾了 Primary Persona（主要角色），而不是试图讨好所有人？
- [ ] 是否在进入详细像素级设计之前，已经充分验证了整体的交互框架（Framework）？
- [ ] 是否在设计过程中持续进行了基于场景（Scenario-based）的逻辑推演？
