# 交互设计工作流：用户目标的挖掘与应用 (User Goals)

## 1. Prerequisites & Context (前提与背景：WHY & WHEN)
> [!IMPORTANT]
> **WHY (为什么关注目标而非任务)**
> 在目标导向设计 (GDD) 的核心哲学中，**任务 (Tasks) 是达成目标的手段，而目标 (Goals) 是最终期望的状态。** 技术和任务可能随着时间演变，但人类的根本目标通常是稳定且持久的。如果仅仅围绕“任务”设计，最终得到的将是一个功能繁琐的堆砌物；围绕“目标”设计，才能创造出直觉般优雅的体验。
> 
> **WHEN (何时应用此工作流)**
> 在用户研究、创建人物角色 (Persona) 的阶段，以及在整个设计过程中作为所有功能去留、优先级排序的最高评判标准。

## 2. Comprehensive Guide & Best Practices (综合指南与最佳实践)

### 2.1 用户目标的三个层级
在构建人物角色时，必须明确以下三个层次的目标：
1. **体验目标 (Experience Goals) - “用户的感觉”**:
   - 这是最本能的层次。用户在使用产品时想有什么情绪？不想有什么情绪？
   - *例子*：“我想感到自己很聪明”、“我不想在同事面前显得笨拙”、“我希望操作能有掌控感”。
   - **设计影响**：决定了视觉设计、交互微动效、反馈机制和容错度的基调。
2. **终极目标 (End Goals) - “用户的成果”**:
   - 用户使用产品是为了完成什么实际的事情。这是交互设计的核心关注点。
   - *例子*：“尽快完成财报以便按时下班”、“找到最便宜且时间合适的航班”、“保持与家人的联系”。
   - **设计影响**：决定了界面信息架构、功能布局和任务流向。
3. **生活目标 (Life Goals) - “用户的长期追求”**:
   - 这是更深远的动机，通常超越了单个产品。
   - *例子*：“成为行业专家”、“过上健康的生活”。
   - **设计影响**：决定了品牌策略、高级内容策略以及如何让产品融入用户的长期生活。

### 2.2 区分非用户目标 (Non-User Goals)
设计时需要兼顾，但**绝对不能凌驾于用户终极目标之上**：
- **商业目标 (Corporate Goals)**: 增加利润、获取用户数据、击败竞争对手。
- **技术目标 (Technical Goals)**: 节省服务器资源、保持架构整洁、使用最新框架。

### 2.3 目标导向的思维转换
- 传统思维（任务导向）：用户必须输入密码、选择目录、点击上传按钮。
- 目标思维（目标导向）：用户的目标是“安全地与朋友分享这张照片”。怎样才能最快达成这一目标，同时省去所有的附加中间步骤？

## 3. If/Then Troubleshooting Logic (故障排除与逻辑分支)

- **IF** 商业目标（如：需要强制用户注册或观看广告）与用户的终极目标（如：立刻查看内容）发生严重冲突：
  - **THEN** 设计师必须寻找“双赢”的交互策略。如采用渐进式参与 (Progressive Engagement)——先让用户体验核心价值达成一部分目标，再在合适的时刻温和地提出注册请求，而非粗暴阻断。如果强推商业目标，将摧毁体验目标，导致用户流失。
- **IF** 工程师以技术困难或维护成本为由，要求用户适应复杂的系统实现模型（增加用户的认知负荷）：
  - **THEN** 利用人物角色的体验目标作为沟通工具。向开发团队说明这种妥协将使人物角色感到“愚蠢和沮丧”，并共同探索是否能在后台承担这些复杂性以保护前台界面的简洁。
- **IF** 发现两个人物角色的终极目标截然相反：
  - **THEN** 明确谁才是产品的**主要人物角色 (Primary Persona)**。如果不能妥协，则次要人物角色的界面可以剥离或隐藏在高级设置中，不能牺牲主要角色的核心目标。

## 4. Verification Checklists (验证清单)

- [ ] 每个核心人物角色是否都明确定义了体验目标、终极目标和生活目标？
- [ ] 交互框架的设计是否直接缩短了达成“终极目标”的路径，而非仅仅优化了“现有任务”？
- [ ] 界面上的文案、视觉和交互反馈是否满足了人物角色的“体验目标”（如不让他们感到受挫）？
- [ ] 产品设计决策中，是否避免了让业务目标或开发技术目标绑架用户的体验？
