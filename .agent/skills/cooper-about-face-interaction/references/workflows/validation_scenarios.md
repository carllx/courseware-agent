# 交互设计工作流：验证场景 (Validation Scenarios)

## 1. Prerequisites & Context (前提与背景：WHY & WHEN)
> [!NOTE]
> **WHY (什么是验证场景)**
> 在早期的需求定义阶段，我们使用“情境场景 (Context Scenarios)”来发散和提取需求。而在交互框架（如线框图、视图结构）初步建立后，我们需要使用“验证场景”来对设计进行压力测试。它是设计的试金石，确保框架能在真实的复杂逻辑中自洽。
> 
> **WHEN (何时应用此工作流)**
> 在交互框架设计 (Interaction Framework) 完成后，进入界面细化 (Refinement) 和最终开发交付前。

## 2. Comprehensive Guide & Best Practices (综合指南与最佳实践)

### 2.1 第一类：关键路径场景 (Key Path Scenarios)
- **定义**: 涵盖用户在产品中最频繁执行的核心交互路径，且假设一切条件都是最理想和顺利的。这必须是完美契合主要人物角色终极目标的路线。
- **验证重点**: 
  - 核心流程是否绝对流畅且没有任何附加工作？
  - 视觉线索是否明确引导用户进入下一步？
  - 是否实现了点击次数与认知负荷的最小化？

### 2.2 第二类：替代场景 (Alternative Scenarios)
- **定义**: 用户正常使用系统时可能产生的不同分支路径，它们是合理的选项，但不如关键路径高频。
- **验证重点**:
  - 用户试图采用不同的方法解决同一问题（如使用快捷键 vs. 菜单）。
  - 有例外的条件但不构成错误（如用户第一次使用，面临的是空状态）。
  - 分支路径是否容易找到，且完成后是否能无缝回到主线？

### 2.3 第三类：边缘场景 (Edge-case Scenarios)
- **定义**: 罕见的极端情况、系统错误状态或异常输入。（例如：断网、两个用户同时修改同一文档、数据库宕机、用户输入了超出预期的极端数值）。
- **验证重点**:
  - 尽管这些情况很少发生，但框架必须能包容它们，而**不破坏关键路径的优雅性**。
  - 错误提示是否具有建设性并提供了恢复路径？

## 3. If/Then Troubleshooting Logic (故障排除与逻辑分支)

- **IF** 为了处理复杂的边缘场景，导致关键路径界面堆满了警告信息、复杂的选项卡或过多的确认按钮：
  - **THEN** 必须进行降级处理。绝不能因为万分之一的边缘场景而惩罚正常走关键路径的用户。将边缘配置隐藏到“高级设置”面板中，或通过非模态的后台通知来处理。
- **IF** 在走查关键路径场景时，发现用户需要反复在两个大板块间跳转：
  - **THEN** 说明当前的交互框架（视图架构）存在根本性缺陷。必须回到框架层，合并相关视图或引入分屏/悬浮面板等模式，消除导航附加工作。
- **IF** 替代场景中的操作过于隐蔽，导致新用户根本找不到：
  - **THEN** 不要在主界面上增加冗余按钮，而是考虑在用户熟悉了关键路径后，通过逐步揭示 (Progressive Disclosure) 或智能提示引导他们发现替代场景的高阶用法。

## 4. Verification Checklists (验证清单)

- [ ] 是否利用关键路径场景成功跑通了交互框架的主线，且确认没有认知断层？
- [ ] 是否测试了当数据为空、数据极多或数据加载缓慢等替代场景下界面的表现？
- [ ] 是否穷举并验证了断网、操作失败、权限不足等边缘场景？
- [ ] 处理异常的边缘场景机制是否完全隐藏或剥离，从而保证了关键路径的极端纯粹与整洁？
