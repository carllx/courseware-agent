# 用户研究：人物角色体系工作流 (Persona)

## Prerequisites & Context (前提条件与上下文)
**WHY（为什么使用）**：
人物角色（Persona）是《About Face》中最核心的概念。如果试图为“所有人”设计产品，最终将无法满足任何人（弹性用户谬误 The Elastic User）。人物角色是基于真实用户研究数据综合而成的“行为原型”，他们具有具体的目标、动机和行为模式。通过为具体的人物角色设计，团队能够终结无穷无尽的意见争论，保持设计焦点的绝对集中。
**WHEN（何时使用）**：
- 完成人种学访谈（研究阶段）后，进入需求定义和设计阶段前。
- 作为所有设计决策的试金石（“我们的主要角色会喜欢这个功能吗？”）。
- 用于团队内部（产品、设计、开发、高管）统一对“目标用户是谁”的共识。

## Comprehensive Guide & Best Practices (综合指南与最佳实践)

### 人物角色的类型与优先级分配 (Persona Types)
一个项目中通常会定义多个角色，但为了避免失去焦点，必须对它们进行严格的类型划分：

#### 1. 主要人物角色 (Primary Persona)
- **定义**：产品**必须**为其服务的最核心受众。如果界面的设计不能满足他们，产品就会失败。
- **规则**：**一个界面只能有一个主要人物角色**。如果发现有两个主要角色，说明你需要为他们分别设计不同的界面（或产品端）。他们的目标驱动着整个界面的结构和交互流。

#### 2. 次要人物角色 (Secondary Persona)
- **定义**：对界面大多满意，但有少量特定的附加需求，而这些需求在不破坏主要角色体验的前提下可以被包容。
- **规则**：通常数量在 1-2 个。例如，主要角色是普通内容创作者，次要角色可能是需要批量导出功能的高级创作者。在设计时，优先满足主要角色，然后再为次要角色“找个地方”放置其专属功能。

#### 3. 补充人物角色 (Supplemental Persona)
- **定义**：他们的需求完全被主要和次要角色的需求所覆盖。
- **规则**：不需要专门为他们进行任何特殊设计。他们的存在只是为了在向利益相关者汇报时证明“我们没有忘记这类群体，只是他们已经被囊括了”。

#### 4. 客户人物角色 (Customer Persona)
- **定义**：掏钱购买产品的人（但不一定是使用者）。常见于企业级软件或儿童产品。
- **规则**：他们的目标通常与管理、成本、安全有关。必须满足他们的商业诉求，但绝不能以牺牲主要使用者（Primary）的日常体验为代价。

#### 5. 被服务者人物角色 (Served Persona)
- **定义**：不直接使用产品，但受产品使用结果影响的人。（如：医院信息系统中的“病人”是不操作软件的，但软件的设计直接关乎其生命安全）。
- **规则**：将其作为一种强有力的约束条件，确保系统不会对他们造成负面影响。

#### 6. 负面人物角色 (Negative/Anti-Persona)
- **定义**：我们明确决定**不**为其设计产品的人。
- **规则**：用于划清产品边界，防止范围蔓延（Scope Creep）。明确“我们不是为极客设计的，所以不要加入复杂的命令行”。

## If/Then Troubleshooting Logic (If/Then 故障排除逻辑)
- **IF** 团队在讨论功能时经常说“有些用户可能会想要这个”，**THEN** 立即打断，要求将“有些用户”具象化。询问：“具体是哪一个 Persona 需要？是主要角色吗？如果是次要角色，这个功能会干扰主要角色吗？”
- **IF** 发现两个角色对界面的核心信息架构产生了完全相反的需求，**THEN** 说明你可能试图把两套产品硬塞进一个界面。必须将其中一个定义为另一款关联产品的主要角色（例如拆分为“客户端”和“商家端”）。
- **IF** 人物角色看起来像是一堆人口统计学数据（如“35岁，已婚，年薪30万”），**THEN** 你的角色是失败的“市场营销角色（Marketing Persona）”。必须重写，将其转化为基于目标和行为（“追求效率，喜欢键盘快捷键，害怕出错”）的设计角色（Design Persona）。

## Verification Checklists (验证清单)
- [ ] 项目中是否明确指定了**唯一**的一个“主要人物角色（Primary Persona）”？
- [ ] 角色的描述是否聚焦于“行为变量（Behavioral Variables）”和“目标（Goals）”，而不是人口统计学数据？
- [ ] 是否设立了“负面人物角色”来抵御不合理的功能请求？
- [ ] 所有的设计决策与功能取舍，是否都能在主要角色的“目标”中找到依据？
- [ ] 角色的构建是否完全基于真实的用户访谈数据，而不是团队在会议室里拍脑袋的臆想（假设角色）？
