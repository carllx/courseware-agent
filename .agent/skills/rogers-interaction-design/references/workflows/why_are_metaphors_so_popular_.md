# 界面隐喻与五大核心交互范式工作流

## 前置条件与上下文 (Prerequisites & Context)
- **为什么需要本工作流**：在产品设计初期，选择合适的交互类型（Interaction Types）能决定产品的基调和用户心智模型；同时，虽然界面隐喻（Metaphors）能帮助新手快速理解复杂系统，但滥用隐喻会导致系统扩展性极差（正如Alan Cooper所批评的那样）。本工作流用于指导团队在隐喻与五大核心交互类型间做出正确的权衡。
- **何时使用**：
  - 当你需要向用户解释或展现一个抽象、陌生的技术概念时。
  - 当你需要为一个新产品定义基础交互方式（例如决定是做成命令行、对话机器人还是空间探索）时。
  - 当现有的界面隐喻随着系统复杂度的增加而显得格格不入时。
- **深入探索**：如需深入了解界面隐喻的局限性与替代方案，请使用 `bash scripts/query_theory.sh "What are Alan Cooper's arguments against interface metaphors?"`

## 综合指南与最佳实践 (Comprehensive Guide & Best Practices)

### 1. 隐喻（Metaphors）的降维与运用框架
1. **隐喻的三大运用层级**：
   - **行为概念化**：如将“实时数据传输”比喻为“水流（Live streaming）”。
   - **结构映射**：如使用物理世界的“卡片（Card）”或“桌面（Desktop）”作为界面的基础结构。
   - **视觉符号化**：如用“购物车（Shopping Cart）”图标代表临时结算区。
2. **警惕隐喻的“扩展性陷阱”**：不要强制为复杂数字功能寻找牵强的物理隐喻（如“配置网络”很难用物理物件比喻）。在复杂系统中，应回归底层逻辑，直接表达概念、功能和对象关系。

### 2. 五大核心交互类型（Interaction Types）匹配法则
根据用户目标和场景，从以下五种类型中选择或组合基础框架：
1. **指令型（Instructing）**
   - **应用场景**：需要快速、高效处理重复性任务（如保存、删除、批量修改）。
   - **设计原则**：提供明确的命令入口（按键、菜单或语音命令），确保系统能精准且快速地执行确定性指令（参考：售货机的指令模式演变）。
2. **对话型（Conversing）**
   - **应用场景**：需要查询特定信息或讨论问题（如CUI、聊天机器人、智能客服）。
   - **设计原则**：系统应扮演“对话伙伴”而非冰冷的执行器，需具备上下文记忆和自然语言解析能力。
3. **操纵型（Manipulating）**
   - **应用场景**：数字内容创作、3D建模或触控界面。
   - **设计原则**：利用用户对物理世界（如推、拉、拖、放）的肌肉记忆，提供即时视觉反馈。
4. **探索型（Exploring）**
   - **应用场景**：VR/AR环境、智能空间体验或游戏。
   - **设计原则**：提供空间导航线索，让用户通过在虚拟或物理环境中的移动来主动发现信息。
5. **响应型（Responding）**
   - **应用场景**：基于位置的服务（LBS）、主动式推荐或系统级通知。
   - **设计原则**：系统主动发起交互（如Netflix弹窗问“还在看吗”），但必须赋予用户“忽略”的权利，避免过度打扰。

## 条件分支与故障排除逻辑 (If/Then Troubleshooting Logic)
- **如果**发现团队在新功能设计上花费大量时间争论“这个图标长得像不像现实中的某个东西”，**那么**应该立刻停止寻找隐喻（Metaphor），转而使用文字标签或标准控件来直接表达功能。
- **如果**用户的核心任务是处理大量枯燥的表格数据，**那么**不要试图引入花哨的“对话型”或“探索型”交互，应坚持使用高效的“指令型”和“操纵型”交互。
- **如果**你设计了一个“响应型”系统（如主动推送周边景点信息），但发现用户频繁关闭通知权限，**那么**说明系统发起的交互过于频繁或相关性差，需调整触发阈值。

## 验证核对表 (Verification Checklists)
- [ ] 界面上的图标和隐喻是否已被证实能在目标受众中快速建立正确的心理预期？
- [ ] 系统的交互类型（指令、对话、操纵、探索、响应）是否与用户的核心任务相匹配？
- [ ] 随着产品功能的增加，现有的界面隐喻是否已经开始产生理解歧义？
- [ ] 对于系统主动发起的“响应型”交互，是否为用户提供了清晰的退出/忽略机制？
