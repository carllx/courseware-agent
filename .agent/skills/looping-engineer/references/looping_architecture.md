# Looping Architecture Patterns

本参考文档详述了在实施 Looping Engineer 时必须遵循的高级工程与架构模式，以确保长效任务的稳定性与预算安全。

## 1. 上下文剪枝 (Context Pruning)

**痛点**：在多轮迭代中，Subagent 会传回大量繁杂的错误日志、冗长的文件内容或无关紧要的搜索结果，极易导致主 Agent 的上下文（Context Window）爆炸，进而“失忆”或做出幻觉判断。

**解决方案**：
*   **状态的外部化 (包括子代理)**：不要试图在聊天上下文中记住长效任务的所有细节。强制使用 Artifacts 来沉淀事实。此外，**严禁子代理通过 `send_message` 发送超长日志**。任何超过 50 行的报错或结果，子代理必须先将其写入 Workspace 临时文件（如 `scratch/error.txt`），仅返回文件路径供主代理按需读取，以彻底切断 OOM 风险。
*   **压缩重传**：当子代理任务失败需要重试时，不要把子代理发来的万字报错全文再回传回去。必须先自行提取核心的“异常特征”、“出错行号”和“已失败的策略清单”，再连同这些浓缩信息派发新指令。

## 2. 避免死锁：策略强制切换 (Strategy Shifting)

**痛点**：基于 LLM 的子代理极易陷入“逻辑死胡同 (Logical Ruts)”，反复输出同一段略作修改但依然无法运行的代码或检索相同的无效关键词。

**解决方案**：
*   **监控行为与进度哈希 (Action/Tool Hash)**：停止仅基于“输出报错相似度”的判断（容易被错误轮换 Error Rotation 绕过）。总控代理必须监控子代理的“工具调用序列”与“全局进度距离”。如果发现工具调用重复或连续 2 轮无实质进展，必须明确注入**硬性黑名单约束 (Hard Bans)**：
    *   *“禁止使用刚才的 xxx 库/思路/关键词，将其视为黑名单”*
    *   *“退回到最初的版本，采用 yyy 替代方案重新寻找破局点”*
*   **最大尝试次数 (TTL)**：设置硬性卡点 `max_iterations = 5`。无论如何不能为了实现单一 QA 目标而无限循环。到达上限必须熔断回滚，保留工件记录并让人类介入。

## 3. Subagent 异步消息路由

在复杂的任务编排中，不仅仅是“主-子”垂直交互，你可以建立网状协同：
*   **测试代理与执行代理的互通**：你可以生成一个名为 `QA Specialist` 的代理和一个 `Coder` 代理。让 Coder 完成后直接将结果通过工作区文件写入，并发送 `send_message` 通知你，你再通知 QA 去执行检查。
*   **利用 `schedule` 实现巡检**：如果任务是长效的集成验证，你可以设置一个 Cron 定时器，让自己定期醒来，拉起一次 Subagent 去巡检特定状态，这构成了真正的无人值守循环。

## 4. 防范无限递归与僵尸代理 (Deadlocks & Privilege Escalation)

**痛点**：多智能体并发容易产生由于逻辑死循环导致的僵尸代理 (Zombie Agents)，并由于无人值守的 Cron 定时器引发严重的权限提权。

**解决方案**：
*   **强制超时断路器 (Failsafe Timers)**：永远不要完全信任 `send_message` 的被动唤醒。每次调用 `invoke_subagent` 时，主控代理**必须**同时调用 `schedule` 设定一个 One-shot timer。如果子代理崩溃失联，定时器能确保主控代理被唤醒并执行回滚。
*   **警惕 `// turbo-all` 提权**：严禁将 `// turbo-all` 权限授予基于不受信外部输入（如 Web 抓取内容、第三方 Issue 评论）触发的 Cron 任务，以防 Prompt Injection 恶意利用系统权限。
