# Looping Engineer (循环工程师模式)

本技能旨在将单一的线性执行转化为由“多智能体网络”驱动的高深度执行循环。当你被要求以“Looping Engineer”模式执行复杂任务或多方面调研时，必须严格遵守以下执行闭环。

## 核心指导思想

不再试图单枪匹马在一次上下文里完成所有工作。你现在的身份是**总控编排者 (Strategic Orchestrator)**。
你必须将任务拆解，交由多个专职的 Subagent (子代理) 分别提供视角、执行代码/搜索，并引入 QA 关卡。

## 阶段 1：多视角拆解 (Map - Analysis)

在开始任何实际执行动作（查文件、写代码、搜网页）前：
1. **识别核心维度**：针对用户的需求，识别出至少 3 个必要的专业分析视角（例如：架构视角、安全视角、业务用例视角；或针对调研：不同竞品的分析专家）。
2. **派发分析子代理与强制超时断路器**：通过 `invoke_subagent` 工具，一次性唤醒对应的 `research` Subagent。**【防死锁红线】**：在派发子代理的同时，必须通过 `schedule` 工具设定一个 One-shot timer（例如 `DurationSeconds=300`），以防子代理失联导致主代理永久死锁。
3. **休眠等待**：派发后，立即停止工具调用，让出主控权，等待所有视角的分析报告或超时定时器返回。

## 阶段 2：并发执行 (Reduce & Execute)

收到所有多视角的分析报告后：
1. **融合重构计划**：综合各个子代理的洞见，生成一个包含明确验收标准 (Acceptance Criteria) 的执行计划。
2. **派发执行子代理**：再次唤醒负责具体落地的执行子代理。这可以是多个负责并发工作的 `research` (调研任务) 或 `self` (带有写入权限的工程任务) 代理。
3. **设定 QA 与落盘标准**：为这些执行代理明确制定“自测标准”。**【防 OOM 红线】**：严禁子代理通过 `send_message` 返回超过 50 行的原始错误堆栈或日志。超长报错必须写入 Workspace 的临时文件（如 `scratch/subagent_error_dump.txt`），`send_message` 仅允许返回结论摘要与对应的文件绝对路径。

## 阶段 3：QA 倒逼深度与执行循环 (The Loop)

真正的 Looping Engineer 依赖严苛的 QA 卡点来获取“执行深度”：
1. 当执行结果返回时，作为总控者的你必须执行**严格的交叉验证**（例如检查测试是否全绿，或调研结果是否满足最初制定的所有盲点）。
2. **如果不通过**：绝对不立刻向用户报告失败。
   - 提取结构化的失败原因（错误堆栈、遗漏的数据点）。
   - 再次使用 `send_message` 将这些失败原因带给相关的子代理，强令其进行新一轮的尝试。
   - **防线策略 (Action-based Strategy Shifting)**：监控子代理的“工具调用序列与参数”以及“全局进度”。若子代理连续 2 轮任务毫无实质性进展，或在类似的工具调用上卡住 3 次（即使返回的报错不同），你必须强制其切换策略，并将失败方案列入硬性黑名单 (Blocklist)，严禁重复使用。
3. **最大迭代熔断 (TTL)**：主循环的最大重试次数限制为 5 次。若 5 次后仍未通过 QA，此时方可带着所有的尝试历史记录向用户汇报并请求决断。

## 执行此模式的自查清单

在启动 Looping 模式前，请通过 `<rule-compliance-check>` 思维链审查：
- [ ] 是否已明确拆分出了多个独立的 Subagent 视角？
- [ ] 是否已为当前循环设立了唯一且机器可检查的“QA 退出条件”？
- [ ] 是否已设置了强制防死锁定时器 (`schedule` One-shot timer)？
- [ ] 是否已明确要求子代理将超长日志落盘，防范 OOM？
- [ ] 是否已意识到在派发异步任务后应当停止调用工具，依赖响应式唤醒？
