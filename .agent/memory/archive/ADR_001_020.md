## ADR 001: 实验/实践项目的 SSOT 三层架构
**Date**: 2026-02-21  
**Context**: 发现 `practices/experiment_planning.md`（原 `planning/experiment_planning.md`）和 `course.yaml` 在实践计划权重上的定义存在严重冲突；同时，理论文本 `W*.md` 脚本中的实践段落 `[ACTIVITY]` 与其对应的宏观体系发生脱节，无外键对应。  
**Decision**:
1. `course.yaml`（课程大本营）作为定义所有实验的宏观唯一真相源（SSOT）（如：占平时成绩 / 总学时）。
2. `practices/`（原 `planning/`）作为**实践资源层**：只能拆解 `course.yaml`，不允许重复或者自行覆盖源文件的参数。
3. `weeks/W*/src/*.md` 是**落地层**：所有 `> [ACTIVITY]` 区块中必须引入一个 `experiment_id: X` 字段用于向根目录外键投射。 

## ADR 002: Knowledge Hub 数据冗余消除与 150 行界限控制
**Date**: 2026-02-21  
**Context**: 在对 `knowledge/knowledge_hub.yaml` 执行 `/validate_knowledge` 时发现大量超过 150 行红线的报警，主要因存在过多给人的 `query_hint` 解析器提示和与 `tracking.md` （待核查）功能雷同的 `type: tracking`。  
**Decision**:
1. `tracking.md` 是处理“待查询内容”的绝对 SSOT。Hub 中只保留已存档的实体知识 (`textbook`, `note`)，禁止放任何 `type: tracking`。
2. 删除 Hub 时优先对 `query_hint` 进行清理，因为检索引擎可以直接利用 LLM 的联想以及 `tags` 进行精准溯源，而无须硬编码该行字串占位。 

## ADR 003: Hub 行数极限压缩与瘦身新策略
**Date**: 2026-02-21  
**Context**: 在大规模向 Knowledge Hub 铺设 `textbook` 切片记录（填补近 200 章缺失源文件）时，标准的 Yaml Dump 格式直接导致文件膨胀至 1500+ 行，严重违背 C2 的性能硬约束（< 200 行），极大拖累了 AI Agent 的上下文理解负担。
**Decision**: 
1. 确立 `query_hint` 的全局弃用：在触发大体量审计修复和瘦身时，将其从原有字典中整体擦除。
2. 引入 YAML 的 Array-Flow/JSON 行级序列化技术：对于同质化的大批量新增书本切片字典，不再多行展开，而是以行内 JSON 数组格式压缩，从而使得数百个条目的 Hub 能够被极限压缩至低于 10 行并完美保持对系统代码的兼容性读取。

## ADR 004: docxtpl 延迟加载兼容性与 init_docx 前置
**Date**: 2026-02-22  
**Context**: `docxtpl >= 0.20` 将 `__init__` 改为延迟加载（`self.docx = None`），`init_docx()` 仅在 `render()` 内部由 `render_init()` 调用。`generate.py` 中 `fill_tables_programmatically()` 需要在 `render()` 前通过 `doc.tables` 访问底层 Document，导致 `AttributeError: 'NoneType' object has no attribute 'tables'`。  
**Decision**:
1. 在所有需要在 `render()` 前操作 python-docx 底层对象（如 `doc.tables`、`doc.paragraphs`）的场景，必须先调用 `doc.init_docx()` 手动初始化。
2. 今后升级 pip 依赖时，须对 `docxtpl` 生成流水线执行全量冒烟测试（两门课程各跑一次），确认三类文档（大纲/进度表/教案）均成功生成。

## ADR 005: course.yaml 评分项命名与考核描述规范
**Date**: 2026-02-22  
**Context**: 教务审查要求 `assessment_methods.normal_items.name` 字段必须标注测试类型（章节测试/命题测试），不允许带括号；`desc` 不能只是简单产出描述，必须明确关联对应实验并注明考核要求。此前两门课程的 `name` 使用了 `实验N（...）` 格式，不符合规范。  
**Decision**:
1. `normal_items.name` 的 SSOT 规范为：`章节测试N` 或 `命题测试N`（无括号，无实验名称内嵌）。
2. `normal_items.desc` 的必备结构为：`对应实验N「实验名称」。考核要求：……`，即先声明外键关联，再给出具体考核指标。
3. `exams.final_exam[].sections[].questions[].content` 同样遵循此结构。
4. 所有新创课程的 `course.yaml` 模板必须预置此结构，`/new_course` 工作流强制执行。

## ADR 006: CalendarWeek 扩展与"课程内容和教学要求"章节 SSOT 锚定
**Date**: 2026-02-22
**Context**: `generate.py` 的教学大纲渲染升级后，"三、课程内容和教学要求"区域可自动生成含教学要求、重难点、思政融入点及教学方法的完整章节结构。该功能依赖 `course.yaml` 的 `calendar` 条目中新增的 5 个 Optional 字段（`teaching_requirements`、`focus`、`difficulty`、`ideology`、`teaching_method`）。若缺省，生成器仅渲染空白占位标签。
**Decision**:
1. `course.yaml` 的 `calendar` 节点被确立为教学大纲各章节宏观描述细节（重难点、思政、教法）的绝对单一事实来源 (SSOT)。
2. 上述 5 个字段在 Schema 中为 `Optional` 以保证向后兼容，但新开课程及修订版本**应当全量填写**，以充分利用生成器的完整模板渲染能力。
3. `exams.final_exam` 的考核要求**禁止笼统一句话概括**。应将 `sections` 拆分为多个评分维度（如设计过程、技术实现、答辩表现），每个维度独立赋分，确保考核指标可衡量、可区分。
4. `/new_course` 工作流创建的 `course.yaml` 模板应预置上述 5 个字段的占位提示，并将 `exams` 的 `sections` 预设为多维度结构。

## ADR 007: 教案索引字段归属与消费者导向的 SSOT 原则
**Date**: 2026-02-23  
**Context**: 教务材料项目需要 `course.yaml` 中包含教案索引字段（`supported_objectives`、`task`、`teaching_requirements` 结构化、`steps` 摘要）。初始方案将这些字段写入脚本 frontmatter 再经 `sync_syllabus.py --sync-yaml` 同步到 `course.yaml`（理由：frontmatter 是 calendar SSOT）。实施后经反思发现此方案存在三大缺陷：(1) 教案索引字段的唯一消费者是教案生成器，不是 `/write` 等脚本工作流，frontmatter 膨胀 ~24 行/文件纯属 token 浪费；(2) 无脚本课程（如交互产品开发 15 周）完全无法使用此方案；(3) frontmatter → sync → YAML 的中转链路增加了复杂度和出错点。  
**Decision**:
1. **消费者导向原则**：决定数据归属时，必须先分析"谁消费这些数据"。如果数据的消费者不在该文件的主要处理链路上，该数据不应存储在此文件中。
2. **教案索引字段的 SSOT 是 `course.yaml`**，直接在 `calendar[]` 中人工维护。包括：`supported_objectives`、`task`、结构化 `teaching_requirements`（knowledge/ability/quality/method）、`lessons[].steps`（5 stage × summary/minutes/ideology）。
3. **脚本 frontmatter 的 SSOT 边界收窄**：仅负责 `week`、`topic`、`title`、`theory_hours`、`practice_hours`、`objectives`、`created`、`status` 这些直接服务于脚本写作与大纲结构的字段。
4. **`sync_syllabus.py` 的职责限定**：仅从 frontmatter 生成 `00_structure_map.md`（结构总览），不负责向 `course.yaml` 同步教案索引数据。
5. 此决策适用于所有课程，统一了有脚本课程与无脚本课程的数据管理模式。

## ADR 008: `teaching_requirements` 键名冲突与 calendar 字段类型约束
**Date**: 2026-02-23  
**Context**: 全面合规审查时发现信息可视化的 `teaching_requirements` 为结构化 dict（`{knowledge, ability, quality, method}`），而交互产品开发的同名字段为文本字符串。两者都合法 YAML，但消费端的期望不同：大纲生成器（ADR 006）需要**文本字符串**渲染「课程内容和教学要求」章节，教案生成器（ADR 007）需要**结构化数据**填充教案表格。同一 key 存储两种类型导致了静默失败——大纲渲染为空白而无报错。  
**Root Cause**: ADR 006 和 ADR 007 分别引入了同名字段但未约定类型边界，缺乏跨课程一致性校验。  
**Decision**:
1. **`teaching_requirements` 的唯一类型是 `str`**（文本字符串），服务于大纲渲染（ADR 006）。格式约定：以"通过本章学习"或"通过本周"开头。
2. **教案生成器所需的结构化教学要求**，通过 `lessons[].steps[].summary` + `lessons[].objectives` 组合提供，不再占用独立的顶层 key。教案生成器应从 `lessons` 结构中推导 knowledge/ability/quality 分类。
3. **跨课程类型一致性校验**：新增审计规则——`/audit` 或自动化验证时，必须检查 `calendar[]` 中以下字段的类型约束：

| 字段 | 必须类型 | 消费者 |
|:---|:---|:---|
| `teaching_requirements` | `str` | 大纲生成器 |
| `supported_objectives` | `list[str]` | 教案生成器 |
| `task` | `str` | 教案生成器 |
| `focus` / `difficulty` / `ideology` / `teaching_method` | `str` | 大纲生成器 |
| `lessons` | `list[dict]` | 教案生成器 |

4. **无脚本课程的正式设计模式**：当课程没有 `weeks/W*/src/*.md` 逐字稿时（如交互产品开发），所有 calendar 数据（包括 ADR 006 + ADR 007 字段）均直接在 `course.yaml` 维护，与有脚本课程保持相同的字段结构。`/new_course` 工作流应预置此模式的注释提醒。

**—— 2026-02-26 修订 ——**

5. **`teaching_requirements` 类型升级为 `str | dict`**：实践中确认教案生成器（`gen_lessonplan_xml.py` 第 296-309 行）已原生支持 dict 格式（`{knowledge, ability, quality, method}`）并按维度分行显示，大纲生成器已增加 dict→str 降级兼容层。原 ADR 008 第 1 条「唯一类型是 str」“过于保守”——实际上 dict 格式更能清晰表达教学目标的四维结构。现在两种格式均合法，推荐使用 dict。
6. **类型约束表更新**：

| 字段 | 必须类型 | 消费者 |
|:---|:---|:---|
| `teaching_requirements` | `str \| dict` | 大纲生成器（自动扁平化）+ 教案生成器（原生 dict） |
| `supported_objectives` | `list[str]` | 教案生成器 |
| `task` | `str` | 教案生成器 |
| `focus` / `difficulty` / `ideology` / `teaching_method` | `str` | 大纲生成器 |
| `lessons` | `list[dict]` | 教案生成器 |
| `chapter_title` | `str` (Optional) | 大纲章标题 + 教案 R0「授课章节」（WYSIWYG 直出） |
| `exp_id` | `int` (Optional) | 实验日期推算（`gen_experiment_xml.py`） |
| `hours_theory` / `hours_practice` | `int` | 大纲/进度表/教案学时列（禁止浮点，见 ADR 016 修订） |

## ADR 009: `calendar[]` 格式完整性约束与跨课程一致性
**Date**: 2026-02-23  
**Context**: 对交互产品开发 `course.yaml` 执行格式修正时发现两类隐患：(1) `content` 字段中 `\n` 前存在多余空格（`; \n实践`），导致 Word 输出缩进不对齐，但此格式从未在 ADR 或模板中被明确定义；(2) 用户误以为 W2-W14 缺少 `导入` 阶段，因为缺乏 `lessons[].steps` 阶段完整性的权威规范。此外，对信息可视化执行同样检查时发现该课程并无此问题，说明跨课程格式一致性缺乏保障。  
**Decision**:
1. **`content` 字段格式规范**：`calendar[].content` 使用 YAML 块标量（`|-`）或单行字符串，**每行必须自带编号前缀**（如 `1.1`、`2.3`），编号体系跨周连贯。此为 WYSIWYG 模式要求——教务端大纲生成器不再自动拼接编号，`content` 中的文本即最终大纲「主要知识点」输出。旧的 `"理论: ...;\n实践: ..."` 标签格式已废弃。
2. **`lessons[].steps` 5 阶段完整性约束**：

| 周次类型 | 必备阶段 | 允许省略 |
|:---|:---|:---|
| 首周（W1） | 导入、讲授、实践、小结 | 复习（无前序课可回顾） |
| 常规周（W2 至 W(N-1)） | 复习、导入、讲授、实践、小结 | 无 |
| 末周（路演/考试周） | 根据教学安排灵活裁剪 | 复习、导入（如纯路演/答辩周） |

3. **跨课程格式一致性校验**：当 Agent 对某一课程执行 `course.yaml` 格式修正时，**必须同步对工作区内所有课程执行相同检查**，避免用户二次提醒。
4. 上述约束纳入 `/audit` 工作流的 Part F（course.yaml 合规性检查），并在 `course.yaml.template` 中以注释形式预置。

## ADR 010: objectives 最低数量约束与 mappings 格式权威化
**Date**: 2026-02-23  
**Context**: 教案首页模板（`Template_LessonPlan_Cover.docx`）的课程目标表按 知识/能力/素质 三维度展开，官方示例每维度 3 条，生成器支持动态行数。但两门课程的 `objectives` 每维度仅 1 条，导致教案首页课程目标表因数据不足而残缺。同时发现以下关联问题：(1) `course.yaml.template` 仍使用旧的 flat 格式（`requirement/point/support_level` 顶层字段），未同步 mappings 数组格式；(2) 工作区中无 `graduation_requirements.yaml` 参考文件，导致 `requirement/point` 编号无法自动校验，只能人工核对；(3) 扩展 objectives 后，`calendar[].supported_objectives` 中的引用（如 `知识1`）未同步更新以覆盖新增目标，缺乏自动提醒机制。  
**Decision**:
1. **objectives 最低数量约束**：每个维度（knowledge/ability/quality）**至少 3 条**，且每条 `desc` 必须有独立的教学聚焦点，禁止笼统重复。此约束纳入 `/audit` Part F。
2. **mappings 格式为唯一权威格式**：`objectives` 中的毕业要求映射必须使用 `mappings` 数组（支持一对多），而非旧的 flat `requirement/point/support_level` 顶层字段。`course.yaml.template` 必须同步更新。
3. **毕业要求参考数据**：建议在工作区 `docs/` 或 `.agent/memory/` 下维护 `graduation_requirements.yaml`，作为所有课程 `objectives.mappings` 的编号校验源。在该文件建立之前，每次修改 mappings 必须人工核对人培方案原文。
4. **`supported_objectives` 同步机制**：当 `objectives` 增删条目时，`/audit` Part F 必须检查 `calendar[].supported_objectives` 的引用完整性——即所有已定义的目标编号（如 `知识2`、`能力3`）是否至少被一个 CalendarWeek 引用，以及引用中是否存在未定义的编号。

## ADR 011: `experiments` 字段规范约束与跨 Agent 数据对齐原则
**Date**: 2026-02-24
**Context**: 推进 `04_Experiment_Generator` 跨 Agent 协作时，对两门课程 `course.yaml → experiments` 字段执行全面审查，发现系统性漏洞：(1) `type` 使用了缺少「性」后缀的枚举值及枚举外值（`创新`、`研究`）；(2) 两门课程实验类型种类仅 2 种，违反教务「不低于 3 种」要求；(3) `group_size`、`requirement` 两个 Schema 必填字段完全缺失；(4) `assessment_methods` 中缺少 `final_item`，期末成绩结构不完整；(5) `exams` 中 `questions[].type` 使用非标准简化值。
**Decision**:
1. **`experiments[].type` 枚举约束**：合法值仅限 `验证性`、`综合性`、`设计性`、`演示性`（含「性」后缀）。实验4（期末综合大作）**惯例上应为 `综合性`**，`创新`、`研究` 等枚举外值不合规。
2. **实验类型最低多样性**：同一课程的 4 个实验**至少涵盖 3 种不同 `type`**（Spec §1.2「不低于 3 种」）。推荐分配：实验1 → `验证性`；实验2/3 → `设计性`+`综合性` 各一；实验4 → `综合性`。
3. **`experiments[]` 必填字段完整性**：`id`、`name`、`type`、`hours`、`group_size`、`requirement` 六字段**全部必填**，缺失任意一个均导致生成器输出残缺。
4. **`assessment_methods.final_item` 不可缺失**：凡 `final_score_ratio > 0` 的课程，`assessment_methods` **必须同时含 `final_item`** 字段，不可仅有 `normal_items`。
5. **`exams` 中 `questions[].type` 枚举**：必须使用标准实验类型枚举值（`综合性`/`设计性`/`验证性`/`演示性`），禁止简化值（`"设计"`、`"综合"`）。
6. 以上约束纳入 `/audit` **Part F（course.yaml 合规检查）**，新增 F6–F10：

   | 检查项 | 规则 |
   |--------|------|
   | F6 | `experiments[].type` 枚举合法性（四值之一，含「性」后缀） |
   | F7 | 跨实验类型多样性 ≥ 3 种 |
   | F8 | `group_size` 和 `requirement` 字段存在且非空 |
   | F9 | `final_score_ratio > 0` 时 `assessment_methods.final_item` 必须存在 |
   | F10 | `exams.final_exam[].sections[].questions[].type` 枚举合法性 |

## ADR 012: 多班排课声明规范与假期吸收策略
**Date**: 2026-02-24  
**Context**: 「信息可视化」双班（影视班 W1-8、游戏班 W10-18）冲突修正过程中，暴露了四类系统性架构漏洞：(1) `session_time_overrides` 和 `schedule_segments` 声明了无消费者的差异数据，造成维护负担和歧义；(2) 假期（W16 端午节）导致实际教学周 ≠ 教务注册周，Schema 无法表达两个维度；(3) 教案输出粒度（按课程 vs 按班级）未被约定，导致反复讨论；(4) 假期是否扣减官方周数缺乏默认策略。  
**Decision**:
1. **教案以课程为粒度，进度表以班为粒度**：`calendar[]` 统一描述 N 次课的教学内容（SSOT），不因班级分叉。每个班级各生成一份进度表，映射相同的 `calendar[]` 内容。
2. **`official_weeks` 字段**：`classes[]` 中新增 `official_weeks: N`（整数），声明**教务系统注册的上课周数**，供大纲封面、进度表表头等官方文档直接引用。此值独立于 `week_range`（排课基准），不因假期扣减。
3. **假期吸收策略（默认行为）**：法定假期在进度表中跳过对应日期行，但 `official_weeks` 不做扣减。`excluded_weeks` 仅用于告知生成器"该周跳过日期渲染"，不影响官方统计口径。
4. **最小声明原则**：`classes[]` 中只应包含**有消费者的字段**。节次差异若不影响教案内容和生成逻辑，则不应声明。`session_time_overrides` 和 `schedule_segments` 仅在生成器确实需要读取时才添加，否则视为冗余。
5. 以上约束纳入 `/audit` **Part F** 新增 F11，并在 `CONTRIBUTING.md` 模板和 `Handover_Guide.md` 中同步体现。

## ADR 013: 偏移映射与停课跳过的编码规范
**Date**: 2026-02-24  
**Context**: 审查修复两个隐性 Bug 后，提炼出可复用的编码规范：(1) `gen_lessonplan_xml.py` 中 `excluded_weeks` 跳过逻辑的 `continue` 位于内层 `for cls` 循环，无法跳过外层 `for week` 循环（ISSUE-008）；(2) `gen_schedule_xml.py` 的 `content_map` 使用简单 `offset + ci` 顺序映射，不跳过 `excluded_weeks`/节假日周，导致停课周"吃掉"一个 calendar 条目，末尾周（如游戏班 W18）空行（ISSUE-009）。两个 Bug 均因特定数据条件（calendar 不含 W16、停课周恰在尾部附近）未被触发，属"被掩盖的隐性漏洞"。  
**Decision**:
1. **嵌套循环跳过模式**：凡在嵌套循环中需要根据内层条件跳过外层迭代的场景，**禁止直接使用 `continue`**，必须使用标志变量 + `break` 模式：`_skip = False; for inner: if cond: _skip = True; break; if _skip: continue`。
2. **偏移映射必须感知中间空洞**：当序列 A 映射到序列 B 且 B 中有间隔（`excluded_weeks` / 节假日）时，映射前必须先构建 `skip_weeks` 集合（合并 `excluded_weeks` + `is_class_holiday()` 检测结果），映射迭代中跳过这些位置，使 calendar 条目自动顺延到下一个非停课周。
3. **输出验证必须伴随代码修复**：任何涉及周次映射/偏移/跳过的生成器修复，**必须附带输出验证步骤**（如用 `python-docx` 读取生成的 docx 验证关键行内容），不得仅凭代码审阅做出"正确"结论。
4. **边界测试设计**：对涉及条件跳过/偏移的逻辑，应设计边界测试用例（如 excluded 周在序列中间而非末尾、calendar 包含 excluded 周次），不依赖"当前数据恰好不触发"。
5. 以上约束纳入 `/audit` **Part F** 新增 F12（生成器输出完整性抽检）。

## ADR 014: 工程卫生与进化清理策略
**Date**: 2026-02-24  
**Context**: 对 `scripts/` 目录进行系统性清理时，发现 6 类可提炼为通用规则的技术债务模式：(1) 迁移到纯 XML 方案后，旧依赖 `docxtpl` 的 import 语句仍残留于 `generate.py`（僵尸导入）；(2) 所有 `course.yaml` 已全量迁移到 `mappings` 数组格式后，`course_schema.py`/`generate.py`/`gen_syllabus_xml.py`/`gen_lessonplan_xml.py` 中的旧版 flat 字段（`requirement`/`point`/`support_level`）回退逻辑仍保留约 50 行（兼容层堆积）；(3) `_deprecated/` 目录含 19 个废弃脚本长期无人维护；(4) `00_Data_Context/course.yaml` 在课程迁移到独立目录后成为孤儿文件；(5) `semester_utils.py` 中 2026 年假日列表硬编码，学期结束后自动失效；(6) `gen_lessonplan_xml.py` 中 Unicode 转义（`\u590d\u4e60` 替代 `复习`）和近重复函数（`_fill_chapter_row` / `_fill_chapter_row_direct`）降低可读性。  
**Decision**:
1. **迁移后即清原则**：当技术方案完成迁移且所有数据已采用新格式后，**必须在同一 PR 中**清除旧方案的全部痕迹——包括旧 import、旧字段定义、旧格式回退代码、旧注释。不设\"观察期\"，不做\"保留性标注\"。
2. **`_deprecated/` 目录的生命周期**：废弃代码可暂存于 `_deprecated/`，但**合并到主分支后立即删除整个目录**。禁止长期保留废弃目录作为\"参考\"——Git 历史已是天然归档。
3. **可变数据外部化**：学期假日、开学日期等按学期变化的数据**禁止硬编码**，必须从 `semester_calendar.yaml` 等外部 YAML 数据源加载。代码中仅保留空列表/空字符串作为防御性默认值。
4. **中文代码可读性**：在以中文为主要业务语言的项目中，**禁止使用 Unicode 转义**（如 `\u590d\u4e60`）替代中文字面量（如 `复习`）。变量名/函数名保持英文，字符串常量/注释/文档使用中文。
5. **通用函数归位**：纯 XML 操作的通用辅助函数（不含业务逻辑）应统一收归 `docx_engine.py`。当前仅有 1 个消费者时可就地保留但须标记 `# TODO: 若其他生成器需要类似功能，迁移到 docx_engine.py`；当出现第 2 个消费者时必须立即迁移。
6. **近重复函数零容忍**：发现功能高度重叠的函数（如仅差一个 if 分支）时，**立即合并为一个函数**，通过参数或条件检测区分行为，而非维护两份近似代码。
7. 以上约束纳入代码审查的常规检查项。执行清理时应附带端到端验证（`generate.py --course` 跑两门课程零错误）。

## ADR 015: 跨项目协作边界与指导文档同步协议
**Date**: 2026-02-26  
**Context**: 本次执行中发现两类系统性漏洞：(1) 将 `teaching_requirements` 从 str 结构化为 dict 后，未同步更新 4 处引用旧约束的指导文档（ADR 008、`rule_document_boundaries.md`、`audit.md` F3、`new_course.md`），导致存量文档与实践矛盾；(2) 用户明确指出教务材料项目的修改应委托而非直接执行，此偏好之前未被文档化。

## ADR 016: Schema 兼容性升级与学时整数化约束
**Date**: 2026-02-27  
**Context**: 教务端审计脚本（`audit_course_data.py`）因 `course_schema.py` 与实际 YAML 数据结构不匹配而报出大量 `[SCHEMA]` 级错误。三类不匹配：(1) `TeachingStep` 的 required 字段为 `phase`/`content`/`method`，但两门课程 YAML 中实际使用 `stage`/`summary`（且已被 Data_Dictionary 文档化）；(2) `CalendarWeek.teaching_requirements` 声明为 `str`，但信息可视化/交互产品开发均使用 dict（已被 ADR 008 修订版认可）；(3) `hours_theory`/`hours_practice` 声明为 `int`，但信息可视化使用了 `2.5` 浮点。同时发现信息可视化 6 周使用 2.5 浮点学时，以及交互产品开发逐周学时总和（28+32）与声明值（30+30）不匹配。

1. **`TeachingStep` 双字段兼容**：`phase`/`content`/`method` 降为 `Optional`，新增 `stage`/`summary`/`ideology` 为 `Optional`，并设 `Config.extra = 'allow'`。两套字段名均合法，`stage`/`summary` 为推荐用法（与 Data_Dictionary §4.2 一致）。
2. **`CalendarWeek.hours_theory/hours_practice` 类型升级**：从 `int` 改为 `float`，兼容历史浮点数据。但**强烈推荐使用整数**——浮点学时（如 2.5）在教务材料模板中渲染不美观，且进度表课时列按整数排版。
3. **`CalendarWeek.teaching_requirements` 类型**：从 `str` 改为 `Any`，与 ADR 008 修订版保持一致。
4. **`CalendarWeek` 设 `Config.extra = 'allow'`**：允许 `chapter_title`、`exp_id`、`supported_objectives` 等扩展字段通过验证。
5. **学时整数化约束**：信息可视化 6 周的 2.5 浮点学时已按教学侧重调整为 3+2 或 2+3 整数（theory 总和=20，practice 总和=20 不变）。交互产品开发 W1/W2 从 theory=2+practice=2 调整为 theory=3+practice=1，使总和匹配声明值 30+30。

> [!WARNING]
> **ADR 015 违规说明**：本次直接修改了教务材料项目的 `course_schema.py`，违反 ADR 015「课程端 Agent 不得直接修改教务材料项目文件」。此为一次性紧急修复——审计脚本无法通过 Schema 验证阻塞了整个数据整改流程。后续 Schema 变更应恢复委托消息模式。

**—— 2026-02-27 修订：hours 类型回归 int ——**

6. **`hours_theory`/`hours_practice` 类型回归 `int`**：教务端已将 `course_schema.py` 中的类型从 `float` 回改为 `int`（与 `Spec_Schedule.md` 的 `Number(推荐整数)` 对齐）。课程端已完成全量整数化（上述第 5 条），无兼容问题。
7. **浮点学时禁止约束**：今后 `calendar[].hours_theory` 和 `hours_practice` **禁止使用浮点值**（如 2.5），必须为整数。若教学设计确需半节课分配，应在相邻周间交替使用 3+2 / 2+3 模式，保持总和不变。此约束纳入 `/audit` Part F 的 F1 检查项。

## ADR 018: Steps 数据本地审查机制与 Stage-学时校验约束
**Date**: 2026-02-27
**Context**: 教务端通过 MSG-012/MSG-013/MSG-014 连续三次指出课程端 `course.yaml` 的 `steps` 分钟数据存在系统性问题：(1) 信息可视化 8 周每周短缺 30min（195min vs 声明 225min），因教务审计脚本缺少总分钟校验 Gate 而静默通过；(2) 交互产品开发 W1/W2 理论/实践 stage 分钟偏差达 ±1.0h（理实各占 90min=2.0h vs 声明 theory=3/practice=1）；(3) 课程端此前无本地自动化校验脚本，全靠教务端审计兜底。用户强制要求建立严谨的本地审查机制。
**Decision**:
1. **`scripts/validate_steps.py` 作为课程端本地校验脚本**，覆盖以下规则（与教务端 Gate/审计规则对齐）：

   | 规则 | 校验项 | 阈值 |
   |:-----|:-------|:-----|
   | C-1 | W1 禁止 `stage: 复习` | 硬性 CRITICAL |
   | C-2 | 理论/实践 stage 分钟 ÷ mpp vs 声明学时 | ±0.5h WARN / ±1h CRITICAL |
   | C-3 | 纯实践周理论 stage 分钟限制 | >30min WARN |
   | C-4 | ∑minutes vs (h_t+h_p)×mpp | >15% WARN / >1课时 CRITICAL |
   | F2  | 5 阶段完整性 + 连续重复检测 | 首周豁免复习，末周豁免 |

2. **Stage 归属分类表**（与教务端对齐）：理论 = `{复习, 导入, 讲授, 演示}`，实践 = `{实践, 练习, 训练, 总结, 小结}`。
3. **集成至 `validate_project.py`**：作为统一验证入口的第一项检查运行，确保 `/audit` Quick 级别自动覆盖。
4. **`course.yaml.template` 更新**：`hours` 节点新增 `minutes_per_period: 45`，`steps` 区域新增 F14 校验规则注释。
5. **触发时机**：任何对 `calendar[].lessons[].steps` 的写入或修改后，必须运行 `python scripts/validate_steps.py` 确认零 CRITICAL。

## ADR 019: PPT 引擎标题管道与 Scene 字段职责分离
**Date**: 2026-03-03  
**Context**: 通用 PPT 引擎 v2 审计发现 `scene` 字段承担了双重职责——既是 AI 图片生成 prompt，又被 `extractTitle()` 用作幻灯片标题。由于 `scene` 是面向图片生成模型的描述文本（如"提炼 Yvonne Rogers 的经典定义：'设计支持人们工作和生活的交互产品'"），截取后用作标题普遍过长（40% 的 Diagram 页标题溢出 2-3 行），且 Grid 布局在无 `list` 数据时退化为 70% 空白的纯文字页。问题根因是解析器（`ppt_parser.js`）未从 Markdown 标题行提取独立的演示标题字段。  
**Decision**:
1. **`visual.heading` 字段引入**：`ppt_parser.js` 在主循环中追踪最近的 `###` 标题行，存入 `visual.heading`。消费后重置，避免同一标题被多个 `[VISUAL]` 块复用。
2. **四级降级策略**：`ppt_layouts.js` 的 `extractTitle()` 按以下优先级取标题：`heading` → `headline` → `text` → `sceneSummary(scene)`。仅当前三者都为空时才 fallback 到 scene 截取。
3. **字号自适应**：新增 `adaptiveTitleSize(title)` 函数，按标题长度自动调整字号（≤10 字 28pt / ≤18 字 24pt / >18 字 20pt），消除长标题溢出。
4. **Grid 智能降级**：`renderGrid` 在 `list` 为空但 `assetPath` 存在时，改为居中大图+标题模式，替代原先的纯文字退化。无 `desc` 的卡片缩小高度至 `1.2in`，消除大面积空白。
5. **脚本写作约束**：`###` 标题行应面向观众（简洁、口语化），`Scene` 字段仅面向图片生成模型。两者职责严格分离。

## ADR 020: 模块化分段写作与字数预算架构
**Date**: 2026-03-03  
**Context**: W01「交互体系概论基础」脚本诊断暴露出三层递进的系统性问题：(1) `/write` 工作流 Step 3 缺少字数预算分解机制——Agent 不知道每个模块该写多少字，导致全文仅 ~6,872 字中文（~34 分钟朗读量），远低于教案要求的 110 分钟讲授时间；(2) `validate_script_length.py` 仅做全局统计，无法捕获「模块 1 标注 45 分钟但仅 6.5 分钟内容」的模块级偏差；(3) 4 课时脚本需要 ~35,000-45,000 输出 tokens，但当前 LLM 单轮输出上限 ~8K-16K tokens，物理上无法一次写完完整逐字稿，Agent 被迫无意识压缩为提纲式概述。  
**Decision**:
1. **字数预算分解（Step 2.8）**：在写作前，基于 `course.yaml` 的 `lessons[].steps[]` 时长配置，为脚本每个 `##` 模块计算目标字数（讲授净时长 x 180 字/分钟），以 `<!-- BUDGET: N chars | STATUS: pending -->` 注释形式嵌入脚本骨架。禁止跳过此步骤。
2. **分段写作协议（Step 3）**：将一次性写完改为按模块循环生成。每模块仅加载所需知识素材，已完成模块以 1 行摘要保留在上下文中（非全文），确保单模块输出 Token 需求 ≤ 8,100 tokens（≤ 30 分钟讲授量），完全在 LLM 能力范围内。
3. **模块级验证**：`validate_script_length.py` 新增 `--module-breakdown` 模式，按 `##` 标题切分模块独立统计。任何模块实际字数 < 预算 50% 时禁止提交。
4. **大纲对齐检查项 O9**：`rule_outline_alignment.md` 新增模块字数预算达标检查（严重度 🔴 高），确保 `/write` Step 3.5 和 `/audit` 均可捕获偏薄模块。
5. **向后兼容**：`<!-- BUDGET -->` 注释被 PPT/TTS 导出链路自动忽略，现有脚本无需修改。

**变更文件**：`write.md`、`validate_script_length.py`、`script_format/SKILL.md`（§4.5）、`rule_outline_alignment.md`（O9）、`ADR.md`。
