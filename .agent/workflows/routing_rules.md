# 课程工作区路由规则（项目专属）

> 本文件仅适用于课程工作区项目，被 `/mailbox_out` 工作流步骤 1 引用。
> **核心原则**：课程工作区项目（`/Users/yamlam/Downloads/2025-2026-2 课程/`）**只负责课程内容与数据**。文档输出格式、Schema 定义、生成器逻辑的修改由教务材料 Agent（`/Users/yamlam/Downloads/教务材料/`）执行。

---

## 何时需要路由判定

当 Agent 收到**修改请求**且可能涉及教务端职责时，在动手之前执行本判定逻辑。典型触发场景：

- 生成的文档格式/排版有问题（模板/生成器 bug）
- `course.yaml` 需要新字段但 Schema 尚未定义
- 审计脚本 `audit_course_data.py` 的校验规则不合理或需增强
- 需要教务端配合调整 Spec 规范
- 多班级排课策略需协商（RFC）

---

## 归属判定表

将修改请求拆分为独立的修改项，逐项对照下表判定归属：

| 归属 | 修改范围 | 示例 |
|:----:|----------|------|
| **课程端** 🟢 | `course.yaml` 数据内容 | topic/content/objectives/experiments 字段值修改 |
| **课程端** 🟢 | 教学脚本 (`weeks/W*/src/*.md`) | 授课讲稿撰写/修改 |
| **课程端** 🟢 | 知识库 (`knowledge/`) | 教学参考资料增删改 |
| **课程端** 🟢 | 课程设计决策 | OBE 目标调整、教学策略变更 |
| **课程端** 🟢 | PPT / 视觉资产 | 课件生成与修改 |
| **教务端** 🔵 | 生成器代码 (`gen_*.py`, `docx_engine.py`) | 输出文档的渲染/格式 bug |
| **教务端** 🔵 | 模板文件 (`Template_*.docx`) | 文档排版/格式调整 |
| **教务端** 🔵 | Schema 定义 (`course_schema.py`) | 新增/修改字段定义 |
| **教务端** 🔵 | 规范文档 (`Spec_*.md`) | 编写规范变更 |
| **教务端** 🔵 | 审计脚本 (`audit_course_data.py`) | 校验规则修改/新增 |
| **双端协同** 🟡 | Schema 新字段 + 数据填充 | 教务端定义字段 → 课程端填充数据 |
| **双端协同** 🟡 | 排课策略协商 | RFC 讨论假期处理/多班差异等 |

### 判定规则

```
IF 修改项仅涉及 course.yaml / 脚本 / 知识库 / PPT:
    → 归属课程端 🟢，直接执行

ELIF 修改项涉及生成器 / 模板 / Schema / Spec / 审计脚本:
    → 归属教务端 🔵 或双端协同 🟡
    → 通过 /mailbox_out 发送 MSG/RFC 给教务材料

ELIF 不确定:
    → 向用户确认归属后再行动
```

> [!CAUTION]
> **严禁**直接修改教务材料项目的文件（`/Users/yamlam/Downloads/教务材料/`）。即使修改看似简单（如改一行 Python），也必须通过 MSG 任务单委托。

---

## 双端协同：课程端先行部分

如果是**双端协同** 🟡，先完成课程端自身的准备工作：

1. **数据就绪**：确保 `course.yaml` 中的数据已符合当前 Schema 要求
2. **验证通过**：运行审计脚本确认无阻塞性错误
3. **需求明确**：整理清楚需要教务端做什么（新字段定义？模板调整？生成器修复？）

---

## 在其他工作流中引用本检查

在 `/write`、`/audit` 等工作流的修改步骤前，添加：

```markdown
### 前置：边界检查
在执行修改前，按 routing_rules.md 判定归属。
- 🟢 课程端项 → 直接执行
- 🔵🟡 教务端项 → 通过 /mailbox_out 发送 MSG/RFC，**不得**直接修改教务材料项目文件
```
